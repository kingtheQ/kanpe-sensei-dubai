# タスク002：冒頭の発音診断（賢者の質問に診断を隠す）

担当：設計＝PM、試作品＝コード担当（Claude）への依頼文はPMが別途用意、精度の判定＝ユーザー本人
版：v1.0（2026-11-15）

## やりたいこと（ユーザーの意向、2026-11-15）

- ゲームの一番最初で、AIの質問に答えるやり取りを通じて、その人がどの発音が苦手かを判別し、ゲーム内の単語の出し方に反映させる。
- 現在の冒頭（賢者が何個か質問して、チケットを選ぶ流れ）自体をAI化できないか。
- **まず精度を確認したい**（いきなり本実装しない）。

## 設計の芯（PM案）

診断用の「テスト画面」は作らない。勉強感が出るため。
代わりに、**賢者の質問への「声の回答」そのものを発音サンプルにする**。

- 【2026-11-15夜に修正】一文ずつ発音させる方式にはしない（本人の指定）。物語のきっかけで「ある程度まとまった文」を話させて、弱点をそこでまとめ上げる。最初の学び方を間違うと無駄な時間になるので、一番初めが肝心、という本人の考えが理由。
- 冒頭全体（賢者とのやり取り＋窓口でのチケット購入）は「単なる質問」では弱い（本人の指定）。プレイヤーが自分の立場とこれからの楽しみを感じ取り、ワクワク感があって記憶に残る体験として設計する。診断はその体験の中に埋め込む。

- 賢者の質問は、答えに狙った音が自然に入るように設計する（例：行き先・日数・荷物・食べ物の質問は、答えに /r/ /l/ /θ/ /æ/ などが入りやすい）。
- プレイヤーは普通に物語の導入として答えているつもりで、裏側では音素ごとの「伝わった／伝わらなかった」を集計する。
- チケット選び（スターアライアンス／ワンワールド）は物語の分岐として今までどおり残し、最後に声で選ぶ。これも回答サンプルの1つになる。
- 判別結果は「苦手な音リスト」として持ち、単語の出し分けは CMU Pronouncing Dictionary の音素タグで絞り込む（実行時AIゼロ、設計バイブル §9）。

## 判定方法の選択肢と精度の正直な話

| 方法 | 何が分かるか | 精度の目安 | コスト |
|---|---|---|---|
| Web Speech API（ブラウザの音声認識）の文字起こしと期待文の比較 | 「どの単語が別の単語に聞き取られたか」から弱い音を**推定**する | 推定どまり。認識側の癖（機種・声質）も混ざる。音素単位の点数は出ない | 無料 |
| Azure 発音評価 | 音素単位の正確さスコア | 採点専用だけあって一番信頼できる | 無料枠 月5時間（アドオン料金の有無は未確認） |

→ 精度確認は2段階にする。
1. まず Web Speech API の推定で「方向性が合うか」を見る（今回の試作品）。
2. 物足りなければ Azure で同じ文を採点し、推定とどこまで一致するか比べる。

## 精度確認の手順（今回やること）

- 試作品ページ：賢者の質問が6つ出て、声で答えると、聞き取り結果と期待した答えを比べて「弱そうな音」の候補を出す。
- **正解データはユーザー本人**：発音教室で習った経験から、自分の苦手な音は分かっている。試作品の推定結果が本人の自覚と合うかどうかで精度を判定する。
- 判定基準（PM案）：苦手な音の上位3つに、本人が自覚している音が2つ以上入っていれば「方向性は合っている」として次に進む。外れたら、質問文（答えに含まれる音の配分）を見直すか、Azure 採点に切り替える。

## 守ること

- 診断結果を「テストの成績」としてプレイヤーに見せない（本実装時）。物語の中では賢者の一言に変える（例：「お主は R の音に旅の苦労が乗りそうじゃ」程度の物語表現は今後の検討事項）。
- 質問は物語の導入として自然なものだけ。発音のための不自然な文を読ませない。
- 精度が確認できるまで、本実装のタスクには進まない。
