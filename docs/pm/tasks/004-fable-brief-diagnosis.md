# Fable依頼文2：発音診断の「まとまった文」の設計

この文をそのまま Claude（Fable）に渡す。期限：火曜0:00 のリセット前。
版：v1.0（2026-11-15、PM作成）

---

あなたは英語学習ゲーム「カンペ先生／空港えいご物語」（世界一周編）の設計担当です。今回はゲーム冒頭に埋め込む「発音の弱点の把握」の設計をお願いします。

## 最初に読むもの

1. リポジトリの docs/rules.md、docs/handover.md
2. tour-src/data.py の冒頭（sage_1/2/3、ticket_star、ticket_ow）と tour-src/ipa.py（発音記号は cmudict ベースで生成されている）
3. Fable依頼文1の成果物（冒頭フロー設計）がある場合は、それに沿う

## 背景と目的

- 目的：ゲームの一番最初に、プレイヤーの発音の弱点を把握し、その後の単語や場面の出し方に反映させる。最初の学び方を間違うと無駄な時間になるので、一番初めが肝心、というのが作成者の考え。
- 作成者の方針（重要）：
  - 一文ずつ発音させる方式には**しない**。物語のきっかけで「ある程度まとまった文」を話させて、弱点をそこでまとめ上げる。
  - 診断用のテスト画面は作らない。勉強している感覚に陥らせないことが、このゲームの一番の原則。
  - 冒頭（賢者とのやり取り＋窓口でのチケット購入）の体験の中に、自然に埋め込む。
- 判定方法は2方式を想定する：①ブラウザの音声認識（Web Speech API）の聞き取り結果からの推定（無料）②Azure 発音評価の音素単位の採点。設計は両方に対応できる形にする。
- 単語の出し分け自体は、CMU Pronouncing Dictionary の音素タグで絞り込む（実行時のAIは使わない）。

## やってほしいこと（成果物4点）

1. **埋め込み設計**：冒頭のどの場面に、どんな物語上のきっかけで、まとまった文を話す流れを作るか。場面案を2〜3個、各案に「きっかけ／話す文の長さの目安／プレイヤーから見た自然さ」を付ける。
2. **診断用の文の候補**：場面に自然で、英語の音を広く含む「まとまった文」の候補を3セット。各セットに、含まれる音の一覧（音素カバレッジ表）を付ける。日本人がつまずきやすい音（語尾のL、F/V、TH、短い母音＋有声子音の語尾など）を意図的に含める。
3. **弱点の集計仕様**：聞き取り結果や採点結果から「弱い音」をどう数え、どう順位付けるか。誤認識（マイクやタイミングの問題）と発音の問題をどう切り分けるかの考え方も含める。
4. **鍛える場面への反映方法**：弱点の音を、その後のどの場面・単語に多く入れるかの反映ルール（試作品STEP3の形を本実装向けに整理する）。

## 守ること

- 診断結果を「テストの成績」としてプレイヤーに見せる設計にしない。物語の中での見せ方にする場合は、その案も書く。
- 「復習」という言葉・画面につながる設計はしない。繰り返しは物語の必然の中で起こす。
- スマホで文字を打つ入力は入れない。入力は発音か、英語の短文を選んで発音するだけ。
- 成果物は「設計案」であり、決定ではない。判定の精度について、根拠のない断言をしない（分かること・推定・未確認を分けて書く）。
