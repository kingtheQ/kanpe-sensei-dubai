## 0. 結論（先に）

1. **終わりの場面は「アルバムの最後の白いページを、声で埋める」。** 1ページ目に旅の最初の約束（宣言文）が貼ってあり、ルルが「最後のページは空っぽ。いっしょに読んで埋めよう」と誘う。誰も「測る」と言わない。マイクを向ける理由が物語の中にある（第1章）。
2. **見せ方は「旅の始めの声」と「いまの声」を、同じ宣言文の上に並べた2枚のページ。** 単語の色の変化を主役にし、4つの数字は小さく添える。点数のランク付け・合否・％表示はしない。いちばん苦手だった音は「次の旅のメモ」（003-12）につなぐ（第2章）。
3. **同意は、最初の送信が起きる宣言の直前に、ゲーム内の1枚で取る。** 「送ってOK／送らない」を同じ大きさで並べ、送らなくても最後まで同じ物語が遊べる。README は書き直しが要る。**いまの README の一文は、Azure を足す前から正確ではない**（Chrome の音声認識は、すでに音声を Google のサーバーに送る）（第3章）。
4. **Azure が使えなくても、場面は壊れない。** 通信できない・同意しない・マイクが使えないの5つの場合を決め、どの場合も「写真が現像されて物語が終わる」まで行く。エラーの言葉は画面に出さない（第4章）。
5. **記録は、新しい保存キー `kanpe-voice-v1` に持ち越す。** 既存の発音記録 `kanpe-pron-v1` は600件で古いものから消えるため、旅の最初の宣言の記録が最後まで残る保証がない。1回の測定は約3.2KB（実測、第5章）。

## 1. 終わりの場面の流れ

### 1-1. 場面の設定

- 場所：旅から帰って1か月後の、家のリビング（007-7）。夜。机の上にアルバム。
- 並び：ルルが左、キングが右（ルール第3章）。ふたりで1冊を見ている。
- 音：静かな部屋の音と、やわらかい音楽。ページをめくる音。**測定用の効果音（開始ブザー・カウントダウン・合格音）は入れない**（004-5）。

### 1-2. 流れ（6画面）

| 画面 | 内容 | 操作 |
|---|---|---|
| E1 ページ1 | 1ページ目に、出発の日の写真と「約束の紙」（宣言文）が貼ってある。ルルが最後のページを指す | タップで進む |
| E2 最後のページ | 最後のページは白い。ルル：「いっしょに読んで埋めよう」。宣言文が紙に出る | キングが宣言文を読む（70語を1ブロック） |
| E3 現像 | 読み終わると、白いページに今日の写真がゆっくり現れる（インスタント写真が現像される感じ）。ルル：「これで1冊そろったね」 | 自動 |
| E4 ふたつの声 | 「旅の始め」と「いま」の宣言文を並べて見る（第2章） | タップで進む／戻る |
| E5 音 | 音ごとの変化（第2章） | タップで進む |
| E6 おしまい | 「次の旅のメモ」と、アルバムの表紙。ここから2周目の入口（007 P12）へ | 閉じる |

目安の長さは、読み上げが約40秒（011）、残りの画面が各5〜10秒で、合計約1.5〜2分。E4〜E5は読み飛ばせる。

### 1-3. 「測られている」感じを出さない工夫

- 誘うのはルル。理由は「アルバムの最後のページが空だから」「1ページ目の約束を、いまの声で読みたいから」。**「もういちど」「チェック」「テスト」「復習」の言葉は使わない**（復習は決定済みで禁止）。
- 読んでいる間は、既存の宣言文と同じ見た目（読んだところが薄く光る）にする。点・色・％は出さない。
- マイクの印は、窓口の宣言文と同じ大きさ・同じ位置。始めと違う見た目にしない（同じ条件にそろえる狙いもある）。
- 結果の画面（E4）は、「写真の続き」として出す。成績表の形にしない。

### 1-4. 台詞の案（英語のみ。日本語は画面に足さない）

| # | 話者 | 台詞 |
|---|---|---|
| 1 | Lulu | Page one. The day we promised. |
| 2 | Lulu | And the last page is still empty. |
| 3 | Lulu | Read it with me, King. Let's fill it. |
| 4 | （キング） | 宣言文（011 の本文70語。そのまま） |
| 5 | Lulu | There. Look how the picture comes up. |
| 6 | Lulu | Now it's a whole album. |
| 7 | King | We went! |

7行目は**採点に入れない「おまけの1言」**。出発の宣言の最後は「Let's go!」なので、終わりは「We went!」で閉じる。宣言文の本文は一字も変えない（変えると比べられない）。

### 1-5. 他の組み立て（候補。キングが選ぶ）

- **案B：声のタイムカプセル。** 1ページ目に、出発の日にキングが言った声の「かたち」が写真として貼ってある（実際の音声は保存しない。第3章）。それに合わせてもう一度言う。物語は強いが、「前の声が残っている」と受け取られやすく、同意の説明が重くなる。
- **案C：ルルの手紙。** ルルが先に宣言文を読み、キングが続ける。圧は弱いが、「真似をして読む」形になり、始めと条件が変わる。
- **案D：音を保存して再生する（声を端末の中だけに残す）。** 始めの声と今の声を聞き比べられて、いちばん胸にくる。ただし「音声は保存しません」の約束を変える最大の変更で、キングの決定が要る。今回の推奨には入れない（確認3）。

推奨は**本案（アルバムの空白のページ）**。理由：物語の自然さが高く、同意の説明が軽く、条件（同じ文・同じ声の出し方）が始めと一番そろう。

## 2. 始めと終わりの並べ方

**注意：** 下敷きにする比較テストページ（Azure発音評価 比較テスト）は、この作業環境から開けず、リポジトリにも入っていない。以下は、タスク指示書に書かれた要素（全体スコア、単語ごとのスコア、いちばん弱かった音の集計、「始め」と「終わり」を並べる）だけから組み立てた。**ページの実物と見比べて調整する必要がある（未確認）。**

### 2-1. 原則

- プレイ中は何も見せない（004-5）。この場面（E4・E5）でだけ開く。
- 点数や％を「勉強の成果表示」にしない。旅の記録として、写真の続きに見せる。
- 色は、赤と緑を使わない。間違いは青（ルール第3章）。波線は使わない。グラデーションは使わない。
- 評価の言葉（「弱い」「ダメ」「合格」「レベル」「診断」）を画面に出さない。「ちょっとむずかしかった音」のように、旅の言い方にする。
- 始めと終わりは**同じ宣言文・同じ測り方**でしか比べない。

### 2-2. E4：ふたつの声（全体と単語）

縦長の画面に、同じ宣言文を2段で重ねる。上が「旅の始め（Departure）」、下が「いま（Home）」。

```
[Departure]   Voice 67  Words 64  Flow 96  Finish 58
 This is my promise, Lulu. We will travel around ...   ← 単語ごとに色
[Home]        Voice 7x  Words 6x  Flow 9x  Finish 6x
 This is my promise, Lulu. We will travel around ...
 ✦ thank  ✦ travel  ✦ world         ← 色が近づいた単語（最大3つ）
```

（数字の2段は例。始めの数字は 2026-11-16 の実機試行の値。「いま」の欄は想像の値なので、実際の数字ではない。）

| 部分 | 案 | 理由 |
|---|---|---|
| 4つの数字 | 小さく添える。ラベルは英語のみ（Voice／Words／Flow／Finish）。**ランクや星にしない** | 数字を消すとキングの「成長の実感」（006-8）が薄まる。大きく見せると成績表になる |
| 単語の色 | 3段階の塗り（平らな色）：近い＝地の色／おしい＝薄い黄／遠い＝青。色だけに頼らず、遠い単語は枠線を太くする | 赤と緑を使わない決まり。色の見分けが苦手でも分かる |
| 変化の見せ方 | 色が一段近づいた単語に、小さな光の印。最大3つ、いちばん近づいた順 | 「ちゃんと成長してる」実感。多く出すと勉強の採点になる |
| 悪くなったとき | 同じ形で出す。悪くなった単語に印は付けない。数字を隠さない。ルルは評価の言葉を言わない | 数字を隠したり、良い方だけ見せたりすると、記録がうそになる |
| 差の読み方 | 数字の上下の矢印は付けない。**5点未満の差は「同じ」とみなす（仮）**。この境目は、同じ人が同じ日に3回測ったときのばらつきで決める | Azure の点は目安で、一回ごとに揺れる（004 3-4）。揺れが分からないうちは境目が決められない（未確認） |

**4つの数字の中の「Finish（言い切り度）」**は、実機試行で58だった。読み切れたかどうかの数字で、発音の上手さとは別。外すか、小さくするかを、キングに決めてほしい（確認4）。

### 2-3. E5：音の変化（いちばんむずかしかった音）

- 単語ごとの音の点を、音の種類ごとに集める（004 3-2〜3-4 の音タグ）。始めと終わりで、**ちょっとむずかしかった音の上位3つ**を並べる。
- 見せ方：音ごとに2本の棒（始め・いま）。棒の横に、その音が入った単語を1つだけ（例：θ → thank）。口の形のイラストは強化合宿のものを使う。
- 数字は出さない（棒の長さだけ）。単語の数字と二重にならないようにする。
- 「別々の単語2つ以上で低かった音」だけを上位に入れる（004 3-5 の切り分けと同じ考え方）。1語だけの低さは、その単語の問題かもしれない。
- 実機試行の低かった語（thank・travel・healthy・world）は、θ・v・語尾のl など、本人が自覚していた弱点と重なった（決定ログ）。この重なりが終わりの画面でも見えるかは、実機で確認するまで分からない（未確認）。

### 2-4. E6：次の旅のメモ

E5でいちばん残った音を1つ、003-12の「次の旅のメモ」に書き足す。「宿題」「課題」とは言わない（勉強の感じが出る）。ルル：「Next time, let's meet that sound on the road.」（案）。2周目の窓口でこのメモが読まれる仕組みは012にある。

### 2-5. 表示の選択肢（全部出す。使いながらキングが消す）

| 項目 | 候補 |
|---|---|
| 数字の見せ方 | ①小さく4つ（推奨）／②総合だけ／③数字なしで色と棒だけ／④設定から開く（初期は閉じる） |
| 単語の並べ方 | ①2段重ね（推奨）／②1段で、始めを上に小さく／③左右2列 |
| 音の見せ方 | ①棒の対（推奨）／②口の形の絵に色／③単語を並べるだけ |
| 変化の強調 | ①光の印（推奨）／②印なし／③ルルが1語だけ口で言う |
| 見られる場所 | ①この場面のみ／②アルバムの棚から何度でも／③設定の記録帳からも |

## 3. 同意の設計

### 3-1. 何が外に出るか（整理）

| 声の行き先 | いつ | 同意 |
|---|---|---|
| ブラウザの音声認識（Chrome は Google、Safari は Apple のサーバー）へ | いまのゲーム全体で、マイクを使うたび | **いまの README に書いていない**（下の注意） |
| Microsoft Azure（発音評価）へ | 旅の始めの宣言と、終わりの宣言の、2回だけ | **新しく取る** |
| 中継（Cloudflare）へ | 声は通らない。「合鍵（トークン）をください」の通信だけ。通信の相手のIPアドレスと時刻は Cloudflare に見える | 同じ画面で説明する |

**注意（READMEの一文）：** README の「音声は保存も送信もしません」は、いまのゲームでも正確ではない。MDN は、ブラウザの音声認識は既定でサーバー型で、音声が外部のサービスに送られると説明している（https://developer.mozilla.org/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API）。Chrome は Google のサーバーに音声を送ると、複数の資料が書いている（確認日：2026-11-16）。Azure を足す前に、この一文を直すのが先。

Azure 側の扱い：Microsoft Learn の「Data and Privacy for Speech to text」は、リアルタイムの音声認識は音声を Azure のサーバーのメモリの中だけで処理し、保存はしない、発音評価では入力の文字起こしを一緒に送ると書いている（https://learn.microsoft.com/legal/cognitive-services/speech-service/speech-to-text/data-privacy-security 、確認日 2026-11-16）。ただし、診断ログ（トレース）を有効にした場合は別（リソース側の設定。キングのリソースでは有効にしないこと。未確認）。

### 3-2. README の書き直し文案

現行：
> 音声は保存も送信もしません。発音の記録は、各自のブラウザ(localStorage)にだけ残ります。

案：
> **声について**
> - このゲームは、声を保存しません。
> - マイクの声は、ブラウザの音声認識で文字にします。ブラウザの種類によって、Google（Chrome）や Apple（Safari）のサーバーに声が送られます。
> - プレイヤーが「送ってOK」を選んだときだけ、旅の始めと終わりの2回、宣言文を言う声が、発音を調べるために Microsoft Azure に送られます。送らなくても、最後まで同じ物語を遊べます。
> - Azure に送るときの合鍵は、Cloudflare の中継が渡します。声は中継を通りません。
> - 発音の記録は、各自のブラウザ（localStorage）にだけ残り、ゲームの運営側には集まりません。

### 3-3. 同意を取る位置と形

- **位置：** 賢者の見送り（sage_3）のあと、宣言（win_decl）の**直前**。最初の送信がここで起きるため。窓口の入口ではなく、紙（宣言文）が出る直前に、ルルから渡す。
- **形：** ゲーム内の1枚の「紙」。ドット絵。ボタンは2つで**同じ大きさ・同じ幅**（スマホの親指に届く）。「送らない」を目立たなくしない。選択に点数・景品・先に進めない仕掛けを結びつけない。
- **一度だけ。** 選択は端末に記録（`kanpe-voice-v1.consent`）。設定の画面から、いつでも変えられる（設定ボタンはすでに全画面にある。新しい項目の追加なので、作る前にキングの確認が要る）。
- 同意が取り消されたら、以降は送らない。すでに端末に残っている結果（Azureの点）は、「声の記録を消す」で消せる。

### 3-4. 同意文の案（日本語）

**ここだけは日本語にしたい。** 「日本語はなるべく使わない」（決定）の例外で、英語が苦手な人が内容を分からないまま「送る」を選ぶのは避けたい。キングの確認が要る（確認2）。

> **声を送ってもいい？**
>
> 旅のはじめと、おわりに、同じ文を言います。
> そのときの声だけを、発音を調べるために Microsoft のサービス（Azure）に送ります。
>
> ・送るのは、この2回だけ。ほかの場面の声は、このサービスには送りません。（ほかの場面では、ブラウザの音声認識が声を文字にします。Chrome なら Google、Safari なら Apple のサービスです。）
> ・ゲームは声を保存しません。Microsoft は、この方法では声を保存しないと説明しています。
> ・結果は、この端末の中だけに残ります。
> ・送らなくても、ゲームは最後まで同じように遊べます。いつでも、設定で変えられます。
>
> [ 送ってOK ]　[ 送らない ]

同意文の括弧の一文は、README 3-2 の2つ目と合わせてある。

## 4. Azure が使えない場合（場面は壊れない）

原則：**どの場合も E1→E2→E3→E6 の物語は同じ。** 変わるのは E4・E5（数字と色の画面）が出るかどうかだけ。エラーの言葉（失敗・接続・Error など）は、画面に出さない。

| # | 場合 | 何が起きるか | 画面 |
|---|---|---|---|
| a | 同意しなかった | Azure は呼ばない。従来のブラウザ音声認識で宣言文を読む（012 と同じ。plog に記録） | E4 は**単語の色だけ**（合った／ちがった の2色。聞こえた文は006-12のとおり表示）。数字なし。E5 は plog の音の集計だけ（方式①）、なければ省略 |
| b | 同意したが、始めの測定がなかった（途中で同意した、始めに通信できなかった） | 終わりだけ Azure で測る | E4 は「いま」の1段だけ。比べず、単語の色と音の棒だけ。ルルは「Let's keep this page.」 |
| c | 終わりに通信できない（オフライン、中継が 429／502／503、トークン切れ） | トークンを取る前に 8秒で見切る。読むところは従来のブラウザ音声認識で続ける | E3 まで同じ。E4 は a と同じ形（聞こえた文と2色）。比較の数字は出さない |
| d | マイクが使えない・許可されなかった | 読む場面は「ルルが先に読み、キングは最後の一言だけ」に切り替える | E1・E2・E3・E6。E4・E5 は出さない。写真は現像される |
| e | Azure の結果が一部だけ返った（途中で切れた） | 返った分だけを使う。半分未満なら、結果を使わず c と同じ扱い | c と同じ |

- 見切りの時間（仮）：トークン取得 8秒、読み終わってから結果が返るまで 12秒。超えたら静かに次の画面へ。
- 「送らない」を選んだプレイヤーにも、**E3 の現像は必ず出る。** 現像は物語の山場で、採点の有無に関係させない。
- 通信できなかったことを、プレイヤーのせいにする言葉を出さない。

## 5. 記録の持ち越し方

### 5-1. 新しい保存キー

既存の `kanpe-pron-v1`（発音記録）は600件で古いものから消える（`plogAdd` の実物で確認）。旅の最初の宣言の記録が、30日分の記録の中で消えると、最後に比べられない。**別の保存キーを作る**（キング確認の対象、確認6）。

```
kanpe-voice-v1 = {
  v: 1,
  consent: { az: true|false, at: 1763300000000, ver: 1 },
  trips: [
    { id: 1,                        // 旅の通し番号（周回）
      ref: 'decl-v1',               // 宣言文の版。同じ版同士だけ、単語ごとに比べる
      start: M, end: M }            // M は下の測定1回分。end は旅の終わりまで null
  ]
}
M = { ts, src: 'az'|'sr',          // az：Azure、sr：ブラウザの音声認識
      tot, acc, flu, cmp,          // 4つの数字（Azure のみ）。sr のときは null
      w: [[word, accuracy, errorType, [[phoneme, score], ...]], ...],  // 宣言文の語の順
      bits, heard }                // 既存 plog と同じ（合った1／ちがった0、聞こえた文）
```

### 5-2. 大きさ（実測）

011 の宣言文70語を cmudict で音に分け、各単語に点を付けた形で JSON 化した：**1回の測定＝3,186バイト**（70語・224音）。1周で始め・終わりの2回＝約6.4KB。ブラウザの保存領域（localStorage、おおむね5MBが目安。**端末ごとの上限は未確認**）に対し、約800周ぶん。サイズの面で問題にならない。

### 5-3. 既存の仕組みとのつなぎ

- **plog（`kanpe-pron-v1`）は今のまま使う。** 宣言・終わりの宣言も、これまでと同じ形で plog に1件ずつ残す（`diag='decl'`／`'decl_end'`）。006-12 の「日常の確認と冒頭のダブルチェック」「あとから見返せる」を守る。
- `kanpe-voice-v1.start` は、plog の同じ `ts` の記録を指して重複しないよう、`bits`・`heard` は voice 側にだけ持つ（plog の `ts` で照合できる）。
- **記録の元になる測定は、同意した人は Azure、同意しない人は sr。** 両方を同じ `M` の形で持ち、E4 は `src` を見て出し方を切り替える（第4章の a〜e）。
- 比べるのは `ref` が同じ測定どうしだけ（単語ごと）。**音ごとの集計は、`ref` が違っても比べられる**ので、2周目で宣言文を変えても、音の変化は持ち越せる。

### 5-4. リセット・2周目

- 「はじめから」で消すかどうかは、設計図「決めること6」が未決（クロ案：旅の記録だけ消し、苦手な音とアルバムは残す）。**このキーは「苦手な音」の側に入れて残す案**（確認6）。
- 2周目の始めは、新しく測り直す案（推奨：同じ宣言文で、同じ条件）と、前の周の「いま」を始めとして引き継ぐ案がある。前者は旅ごとの変化がはっきり見え、後者は測定が1回少なくて済む。
- 旅の途中の測定（宣言文以外の発音記録）は plog にそのまま残り、この場面では使わない。

### 5-5. 実装の入口（次の作業に渡す情報）

- 始めの宣言（win_decl）で、同意した人にだけ Azure を使う。Azure の SDK は `fromAuthorizationToken(token, region)` でトークンを渡す（Microsoft の JS SDK 資料で確認）。70語は約40秒で、30秒を超える音声は連続認識で扱う（Microsoft Learn の発音評価の説明）。
- 同意した人の宣言は、Azure が文字起こしも返すので、**Azure だけで読ませ、ブラウザの音声認識を同時に動かさない**（マイクを2つが同時に使う不具合を避ける案。端末ごとの動作は未確認）。そのとき plog には、Azure の結果から同じ形の記録を作って入れる。
- 抑揚（prosody）などの上乗せ機能は、料金が別（`relay/SETUP.md` の費用の項）。使わない。
